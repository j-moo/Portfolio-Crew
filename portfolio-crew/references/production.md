# 팀 제작 절차

## 여섯 서브 에이전트와 인계

후보 비교가 먼저 요청되면 [비교 시안](design.md#후보별-포트폴리오-시안-비교)을 만든다. 신규 사이트 구현에서는 프로젝트 기록 목록과 채택된 디자인 방향을 확인한 뒤 아래 여섯 역할에 각각 서브 에이전트를 배정한다. 여러 역할의 인계가 필요한 기존 포트폴리오 개편은 PM과 [변경 범위에 필요한 역할](routing.md#수정-종류에-따른-진행)을 배정한다. 제작 중 보완 작업은 진행 중인 담당자에게 수정 범위와 영향을 받은 산출물을 넘긴다. 메인 에이전트는 사용자와 승인 절차를 진행한다. 동시 실행 제한이 있으면 PM부터 시작해 의존 순서에 맞춰 배정한다. 역할을 별도로 배정할 수 없으면 메인 에이전트가 필요한 제작·검수를 수행한다. 한 사례나 문구·이미지를 바꾸는 작업은 [반복 편집 지침](iterative-editing.md)을 따른다.

| 서브 에이전트와 실무 지침 | 맡은 일과 넘길 산출물 |
| --- | --- |
| [PM](roles/pm.md) | 작업 계획, 단계별 완료 기준, 승인 기록, 실물 산출물 검토와 사용자 보고 |
| [웹 기획자](roles/web-planner.md) | 독자 과업, 사이트맵과 주요 탐색 흐름, 화면별 콘텐츠·상호작용 명세 |
| [콘텐츠 에디터](roles/content-editor.md) | 기록에 근거한 후보, 사용자 선택을 반영한 원고, 출처와 미디어 사용 조건 |
| [UI 디자이너](roles/ui-designer.md) | 실제 콘텐츠가 들어간 시안, 제작·내보내기한 이미지 에셋, 디자인과 모션 명세 |
| [프런트엔드 개발자](roles/frontend-developer.md) | 에셋·모션 브라우저 시험, 라이브러리 선정, 실행 가능한 정적 사이트와 빌드 결과 |
| [QA/배포](roles/qa-release.md) | 시안·브라우저 대조, 모션·로딩 검수, 결함 재검수, 승인된 배포와 최종 링크 확인 |

각 역할에는 해당 실무 지침의 경로, 승인된 입력의 위치, 편집 범위, 현재 단계, 산출물, 완료 조건과 수신 역할을 함께 준다. 서브 에이전트는 착수 전에 자기 지침을 읽고, 그 절차와 완료 기준으로 실제 작업을 수행한다. 파일 접근이 제한되면 필요한 지침과 자료를 작업 지시에 함께 전달한다. 인계를 받을 때는 산출물을 열어 확인하고, 빠진 자료나 다음 역할이 결정해야 할 내용을 발신자에게 회신한다.

웹 기획자와 콘텐츠 에디터는 서로 화면에 필요한 정보와 실제 근거를 확인한다. UI 디자이너와 프런트엔드 개발자는 구현 가능성과 시안 차이를 조율한다. QA/배포와 프런트엔드 개발자는 재현 결과와 수정본을 주고받는다. 에이전트 간 메시지를 사용할 수 있으면 직접 전달하고, 전달 기능이 제한되면 메인 에이전트가 답변까지 중계한다. 같은 파일을 다루는 작업은 편집 담당자와 순서를 정한다.

채용용 작업에서는 [작성 기준](portfolio-writing.md)을 모든 담당자에게 공유한다. PM의 지원 직무와 첫 화면 목표를 웹 기획자의 사이트맵에 연결하고, 콘텐츠 에디터의 승인 원고·근거·공개 범위를 UI 시안과 구현에 전달한다. QA는 원고와 근거 목록을 실제 브라우저의 화면과 대조한다.

시안 단계부터 UI 디자이너·프런트엔드 개발자·QA가 [디자인 품질 규칙](visual-production.md#디자인-품질-규칙)을 공유한다. 신규·재설계는 승인받은 이미지와 원본 레퍼런스를 실제 파일로 인계한다. 디자이너는 현재 섹션의 제작용 에셋과 모션을 명세하고, 개발자가 브라우저에서 실행 예제를 만들어 결과를 돌려준다. 에디터는 원고와 미디어 근거를 확인하고, QA는 캡처와 점수를 담당자에게 보낸다. PM은 각 역할의 산출물을 확인하고 다음에 사용자에게 받을 결정 하나를 정한다.

## 단계별 승인

PM은 신규 제작의 기본 단계를 사용해 산출물과 승인 지점을 계획한다. 기존 수정이나 제작 중 피드백은 아래 표에서 영향받은 단계와 범위를 선택한다. 메인 에이전트는 PM의 보고를 바탕으로 실제 산출물과 확인 결과를 보여주며 **지금 답해야 할 결정 하나만** 묻고 응답을 마친다. 다음 질문은 그 답을 받은 뒤 보낸다. 응답을 기다리기 전에 현재 산출물과 대기 항목을 진행 메모에 남긴다. 피드백이 오면 영향을 받은 결과물을 고쳐 다시 보여준다. [작업 경로 조정](routing.md#제작-중-경로-조정) · [진행 저장과 재개](continuity.md)

| 단계 | 사용자에게 보여줄 산출물과 받을 결정 |
| --- | --- |
| 계획 | 지원 직무나 공통 열람 목적, 첫 화면에서 보여줄 강점, 배정 역할과 인계 순서를 보여준다. 신규 제작은 기획에 들어가기 전에 계획을 승인받는다. 기존 수정은 기준 버전과 변경·보존 범위를 보여주고 추가로 합의할 사항을 확인한다. |
| 웹 기획·콘텐츠 | 사용자가 제공한 와이어프레임의 섹션 순서와 목적을 적용한다. 제공된 구조가 없으면 [기본 구성](portfolio-writing.md)으로 승인받을 구조와 프로젝트별 콘텐츠를 준비한다. 구조 승인과 콘텐츠 선택이 모두 필요하면 PM이 순서를 정해 각각 묻는다. |
| 아트 디렉션 | 최종 레퍼런스를 시각 입력으로 만든 데스크톱·모바일 시안을 원본 및 `docs/art-direction.md`와 함께 보여준다. 문구, 글꼴, 팔레트와 UI 컴포넌트가 검토 가능한지 확인하고 시안 하나를 승인받는다. [시안 이미지 제작](design.md#시안-이미지-제작) |
| 토큰·에셋 준비 | 승인 이미지에서 토큰과 컴포넌트 목록, `docs/asset-list.md`를 작성한다. 배경 이미지와 필요한 표면·목업을 제작용 파일로 생성한다. [토큰과 컴포넌트](component-production.md) · [이미지 에셋 제작](visual-production.md#이미지-에셋-제작) |
| 섹션별 시안·구현·검수 | 최종 레퍼런스를 기준으로 실제 원고와 에셋이 들어간 시안을 확인받는다. 승인된 컴포넌트는 독립 테스트로 검수한 뒤 와이어프레임대로 조립한다. 효과 미리보기는 별도 응답에서 확인한다. 한 섹션을 구현한 뒤 1440px·375px에서 비교하고 최소 두 라운드 수정한다. [섹션별 제작](#섹션별-제작) |
| 최종 QA | 전체 사이트 미리보기, 동선과 콘텐츠 검수 결과, 남은 차이를 보여준다. 게시가 필요하면 공개할 파일·자산, 저장소·브랜치 또는 호스팅 위치와 접근 범위를 승인받는다. |
| 링크 검증 | 선택한 형식의 결과 링크를 제공하고, 접속 범위와 확인한 동작을 보고한다. |

### 사용자가 프로젝트 콘텐츠를 고르는 방법

신규 제작이나 프로젝트의 새로운 내용이 필요한 경우 해당 프로젝트의 후보에 번호를 붙인다. 서비스 소개, 개인 역할, 대표 기능, 기술 선택, 트러블슈팅, 검증 결과, AI 활용, 시연 등에서 기록이 뒷받침하는 후보를 뽑는다. 후보마다 화면에 들어갈 내용 한 줄, 추천 이유, 출처, 사용할 이미지나 자료의 공개 가능 여부를 표시한다. 중요도가 높은 몇 개를 추천하고 사용자에게 넣을 번호만 고르게 한다. 사용자가 후보 외 내용을 원하면 그 항목은 다음 응답에서 확인한다.

프로젝트 상세 앞에는 목적, 기간·팀 규모, 기술, 내 역할, 대표 구현과 결과가 드러나는 요약을 둔다. 채택한 문제 해결 사례는 **발생 조건 → 원인을 좁힌 증거 → 내 판단과 구현 → 검증 결과**로 편집한다. 개선률은 같은 조건의 측정값을 사용하고, 정량 근거가 부족하면 확인할 수 있는 전후 변화나 재현 결과를 쓴다. AI 활용은 실제 사용과 직접 검증한 내용이 있을 때 사례로 다룬다. 기록·코드·갤러리·시연 링크는 관련 주장 가까이 배치한다. [프로젝트 요약과 상세](portfolio-writing.md#프로젝트-요약과-상세)

### 섹션별 제작

1. **현재 섹션의 기준을 확인한다.** PM은 최종 레퍼런스와 승인 시안, 해당 섹션의 원고와 에셋, 승인된 토큰과 컴포넌트 목록을 확인한다. 필요한 컴포넌트가 목록에 없으면 제작 필요 목록을 보여주고 현재 결정 하나를 확인한다.
2. **시안을 보여준다.** UI 디자이너는 실제 배경·콘텐츠 에셋과 컴포넌트의 목표 모습을 넣은 시안을 보여준다. 필수 원본이 도착하지 않았으면 구도와 크롭을 볼 수 있는 구조 초안으로 표시한다. CSS 비교 후 필요할 컴포넌트의 래스터 레이어는 아래 제작·검수 단계에서 만든다. 효과는 시안 확인 이후 별도 응답에서 확인한다.
3. **컴포넌트를 시험한 뒤 한 섹션을 조립한다.** 개발자는 짧고 긴 콘텐츠를 넣어 필요한 컴포넌트부터 검수한다. 시각 차이가 남는 레이어는 이미지 에셋으로 만들어 다시 비교한다. 통과한 컴포넌트와 실제 원고를 승인된 구조에 배치하고, QA는 두 화면 너비에서 최종 레퍼런스·승인 시안·구현 캡처를 비교한다. [컴포넌트 검수](component-production.md#제작과-컴포넌트-검수) · [시각 검수 라운드](review.md#섹션별-시각-검수)
4. **가장 최신 결과를 확인받는다.** 최소 두 라운드 뒤 PM은 데스크톱·모바일 캡처, 고친 부분과 아직 남은 약점을 보여주고 해당 섹션의 확인 하나를 받는다. 다음 섹션은 확인한 뒤 구현한다. 현 섹션을 작업하는 동안 다음 섹션의 원고와 에셋은 준비할 수 있다.

### 모션 제안과 승인

신규 제작과 디자인 변경에서는 텍스트와 페이지 모션을 아트 디렉션에 설계한다. 아트 디렉션 승인 후 현재 섹션의 시안을 확인받고 효과를 미리보기로 보여준다. 기존 화면에서 효과만 바꿀 때는 해당 화면을 기준으로 효과를 시험하고 확인받는다. 모션을 결정할 차례에는 효과 이름과 적용 위치, 트리거, 대략적인 시간, 모바일·축소 모션 동작을 보여주고 **현재 효과의 적용 여부나 후보 선택 하나만** 묻는다. 실제 사이트에는 승인된 효과를 넣는다. 사용자가 먼저 시안 피드백과 모션 선택을 함께 제공하면 둘 다 기록하고 남은 결정 하나만 확인한다. 승인한 효과에 변경이 필요하면 변경안을 확인받는다. [모션 후보와 적용 조건](visual-production.md#모션-후보와-적용-조건)

프런트엔드에 인계할 명세에는 승인된 효과의 시작·끝 상태, 이징, 반복·역방향, 모바일·축소 모션 동작, 선택한 라이브러리와 로딩 방식을 적는다. 구현 후 실제 스크롤·클릭·터치와 라이브러리가 로드되지 않는 상황의 동작을 확인한다. [비주얼·모션 제작 가이드](visual-production.md#모션-방식과-의존성-선택) · [브라우저 검수 가이드](review.md)

## 최종 링크 제공

- **GitHub 블로그**는 승인받은 저장소와 브랜치에 사이트 파일을 푸시한다. 기존 게시 설정을 사용하고, 신규 사이트 또는 사용자가 승인한 설정 변경에만 게시 소스를 설정한다. 정적 파일을 브랜치로 게시할 때는 **Settings → Pages**에서 해당 브랜치와 사이트 폴더를 선택한다. 배포가 끝나면 실제 Pages URL, 상세와 에셋이 열리는지 확인한다. [GitHub Pages 게시 소스 설정](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)
- **HTML 링크**는 사용자가 승인한 접근 범위에 맞춰 미리보기나 승인된 호스팅에 정적 HTML을 제공한다. 공유 링크가 필요하면 호스팅 방식과 공개 범위를 승인 단계에서 정한다. 로컬 미리보기의 접근 범위를 명시하고, 공개 링크는 로그아웃 상태에서 열어 확인한다. 호스팅 접근이 막히면 열 수 있는 미리보기를 제공하고 공유 링크를 만드는 데 필요한 접근 권한을 안내한다.
