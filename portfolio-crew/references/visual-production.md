# 비주얼·모션 제작과 인계

레퍼런스에서 보존할 특징을 화면에서 확인 가능한 기준으로 정하고, 실제 콘텐츠가 들어간 화면에서 검증한다. 신규 제작은 첫 화면과 대표 상세를, 일부 수정은 기준 사이트와 영향받은 화면을 대조한다. 디자인, 구현, QA는 [단계별 승인](production.md#단계별-승인)을 공유한다.

## 시각적 특징을 작업 항목으로 바꾸기

UI 디자이너는 [레퍼런스 분석](design.md)과 작업 범위를 확인한다. 신규·전면 디자인에서는 공통 특징과 상위 세 레퍼런스가 맡은 역할을 정한다. 일부 수정에서는 해당 화면의 레퍼런스와 기존 스타일을 기준으로 변경 요소만 정한다. 사진 배치, 제목과 여백의 관계, 재질·층·빛, 상세 진입 모션처럼 이번 요청의 인상을 좌우하는 항목을 우선한다. 항목마다 다음을 메모하고 해당 작업에 참여하는 역할과 공유한다.

| 기록할 항목 | 작성 기준 |
| --- | --- |
| 근거 | 레퍼런스 번호와 해당 장면, 포트폴리오에서 적용할 위치 |
| 검수 기준 | 데스크톱과 모바일에서 관찰할 특징, 유지할 읽는 순서와 상호작용 상태 |
| 제작 방식 | HTML·CSS, 보유 에셋, 제작할 이미지, 모션 라이브러리 중 필요한 방식과 담당자 |
| 확인 자료 | 실제 원고가 들어간 시안, 사용한 에셋 파일, 브라우저 캡처나 짧은 동작 영상 |
| 결정 | 선택한 결과, 남은 차이, 수정 담당자, 해당 버전에 대한 승인 상태 |

웹 기획자는 대표 장면이 탐색을 어떻게 돕는지 확인한다. 콘텐츠 에디터는 시안에 넣을 실제 문구와 서비스 화면을 제공한다. 두 역할은 모바일에서 필요한 정보와 DOM으로 유지할 제목·링크·버튼을 디자이너에게 알려준다.

## 이미지 에셋 제작

1. **레이어를 나눈다.** 제목, 프로젝트 정보, 버튼, 내비게이션은 반응형 HTML·CSS로 구성한다. 사진·종이 질감·반투명 장식·복잡한 조명·일러스트처럼 화면의 인상을 만드는 부분은 독립 에셋으로 검토한다. CSS 구현으로 목표한 질감이나 형태가 나오지 않으면 실제 이미지 제작·내보내기로 전환한다.
2. **재료와 제작 수단을 정한다.** 실제 서비스 기능을 보여주는 스크린샷이나 시연은 프로젝트 기록에서 공개 가능한 원본을 확보한다. 장식·배경·오브젝트는 사용이 승인된 자산을 편집하거나 이미지 생성 도구로 원본을 만든다. ImageGen을 쓸 수 있으면 해당 지침에 따라 목적, 크롭, 색감, 투명 배경이 필요한지를 명확히 전달한다. 필요한 도구나 자료가 없으면 디자이너는 PM에게 확보할 에셋과 사용 가능한 대안을 알려준다. 레퍼런스의 사진이나 로고를 그대로 공개하려면 사용 조건을 확인한다. 비공개 자료는 승인된 사용·전송 범위 안에서 다룬다.
3. **디자인과 개발이 에셋 규격을 맞춘다.** 디자이너는 실제 표시 크기와 비율, 데스크톱·모바일 크롭, 안전 여백, 투명 영역과 겹치는 순서를 지정한다. 개발자는 첫 화면에서 바로 로드할 에셋과 지연 로드할 에셋, 내보낼 크기와 포맷을 제안한다. 알파 채널이나 이미지 품질이 필요한 곳에서 PNG 또는 적합한 WebP를 선택하고 실제 용량을 확인한다.
4. **사용할 파일을 전달한다.** 에셋 목록에 화면별로 파일 경로, 크기와 비율, 포맷, 출처나 생성 방법, 공개 가능 범위, 크롭 기준, 대체 텍스트 또는 장식 여부를 적는다. UI 디자이너는 실물 시안에 파일을 넣고, 프런트엔드 개발자는 실제 배경과 글자 위에서 프레이밍·투명도·크기를 확인한다. 생성한 장식과 실제 서비스 증거는 각자의 용도로 표시한다.

## 모션 방식과 의존성 선택

UI 디자이너와 프런트엔드 개발자는 효과별 목적과 복잡도를 보고 도구를 고른다. 포트폴리오의 주요 장면에서는 동일한 시안으로 짧은 실행 예제를 만들어 의도한 리듬과 사용성을 확인한다.

| 구현할 효과 | 우선 검토할 방식 |
| --- | --- |
| 포커스 표시나 짧은 호버 색상 변화 | CSS의 상태 스타일과 짧은 전환 |
| 여러 요소가 연결된 타임라인, 스크롤 진행에 따라 움직이는 장면, 구간 고정·순차 등장 | **GSAP + ScrollTrigger**로 타임라인과 스크롤 조건을 검증한다. [ScrollTrigger 공식 문서](https://gsap.com/docs/v3/Plugins/ScrollTrigger/) |
| 스프링 기반 카드 상호작용, 제스처, 컴포넌트 상태·레이아웃 전환 | **Motion**을 검토하고 해당 기능의 프레임워크 또는 JavaScript 지원을 확인한다. [Motion 공식 문서](https://motion.dev/docs) |

- 기존 프로젝트에 패키지 관리와 빌드가 있으면 선택한 패키지와 버전을 기록하고 잠금 파일로 재현한다. 빌드 없는 정적 HTML이면 공식 설치 안내에서 CDN 또는 로컬 배포 방식을 확인하고 실제로 확인한 버전을 고정한다. GSAP과 플러그인을 함께 쓸 때는 호환 버전과 로딩 순서를 확인한다. [GSAP 설치](https://gsap.com/docs/v3/Installation/) · [Motion 설치](https://motion.dev/docs/quick-start)
- 개발자가 실행 시험과 호스팅 환경을 근거로 패키지·CDN·로컬 파일 중 한 방식을 제안한다. QA는 로딩과 실패 시 동작을 확인하고, PM은 선택한 버전과 방식을 제작 기록에 남긴다. 전달 방식을 변경해도 승인된 화면·효과·공개 범위를 유지하면 그 승인을 사용해 같은 기준으로 재검수한다. 이 범위를 바꿔야 하면 달라지는 모습을 보여주고 해당 변경을 확인받는다.
- 모션 명세에 입력과 트리거, 초기·종료 상태, 시간과 이징·순차 간격, 역방향·연속 입력, 모바일·키보드·축소 모션 설정을 적는다. 의존성 이름과 버전, 로딩 방식, 실패 때의 동작을 같이 넘긴다.
- 외부 스크립트가 지연되거나 로드에 실패해도 제목, 콘텐츠, 탐색 링크가 브라우저에서 작동하도록 기본 화면을 유지한다. 축소 모션에서는 콘텐츠를 즉시 표시하거나 승인된 간단한 상태 전환을 사용한다. 크기 변경과 화면 재진입에서 리스너나 타임라인이 중복되면 정리한다.

## 에이전트 간 시안 검토와 반영

1. **UI 디자이너 → 개발자·에디터.** 레퍼런스 번호와 목표 장면, HTML 레이아웃, 필요한 실제 문구·스크린샷·장식 에셋, 동작 명세를 전달한다. 에디터는 실제 결과를 보여주는 자료의 출처와 사용 범위를 회신한다.
2. **개발자 → 디자이너·QA.** 적용이 어려운 재질이나 동작이 있으면 시안 단계의 격리된 미리보기에서 에셋 규격과 모션 방식을 시험한다. 현재 시안과 브라우저 비교 화면, 부족한 점, 패키지나 CDN 선택, 필요한 파일과 예상 대체 동작을 돌려준다. 사용자 승인 후 선택한 효과를 제작 사이트에 넣는다.
3. **디자이너·QA → PM.** 시안 단계에서는 시안 초안과 효과 제안을 기준으로 격리 미리보기를 평가하고, 구현부터는 승인된 시안과 효과를 기준으로 정식 검수한다. 같은 화면 폭에서 질감·크롭·타이포그래피와 모션 타이밍의 구체적인 차이, 축소 모션·CDN 실패 시 동작과 수정안을 캡처나 영상으로 남긴다. 차이가 의미 있으면 담당자를 정하고 수정본을 다시 대조한다.
4. **PM → 메인 에이전트와 사용자.** 실제 콘텐츠가 든 영향 범위의 시안, 해당하는 효과 미리보기, 확인한 차이와 남은 선택을 전달한다. 사용자에게 수정안과 효과별 선택을 보여준다. 여러 화면에 적용하는 계획이면 승인받은 대표 화면과 효과를 해당 범위에 확장한다.

PM은 이번 작업에 필요한 시안과 효과의 적용 승인을 기록한다. 시안과 효과는 한 보고에서 함께 확인받을 수 있다. 여러 화면에 대표 구현을 적용하는 경우 대표 브라우저 결과를 보여준 뒤 확장 승인을 받는다.

예를 들어 첫 화면 레퍼런스의 종이 질감과 순차 등장이 중요하다면, 디자이너가 종이결 배경을 별도 이미지로 만들고 제목과 카드의 글자를 HTML로 배치한다. 개발자는 카드가 스크롤 구간에 맞춰 순차 등장하는 장면을 GSAP과 ScrollTrigger로 시험해 보여준다. QA는 같은 화면 폭에서 질감과 크롭을 대조하고, 작은 화면과 축소 모션 설정에서도 카드와 링크가 바로 읽히는지 확인한다.
