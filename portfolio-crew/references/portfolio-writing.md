# 채용용 웹 포트폴리오 작성 기준

GitHub 블로그와 HTML 포트폴리오의 기획·원고·검수에 이 기준을 적용한다. 기존 사이트 수정은 요청한 항목과 그에 연결된 근거에 적용한다.

## 공통 콘텐츠 템플릿

새 포트폴리오는 다음 항목과 읽기 흐름을 출발점으로 삼는다. 이 명세는 다른 작업 폴더에서도 그대로 사용할 수 있다. 이름·소개·기술·경험·프로젝트·미디어는 해당 사용자의 기록으로 채우고, 자료가 없는 선택 항목은 생략한다. 기존 사이트의 부분 수정에는 요청한 범위만 적용한다.

| 열람 흐름 | 담을 내용 |
| --- | --- |
| 랜딩 → 소개 | 직무와 강점을 담은 한 문장, 이름·역할. 소개에는 프로필, 일하는 방식, 공개 가능한 사진·연락 수단을 둔다. |
| 기술 → 교육 | 실제 사용한 기술을 역할별로 묶고, 교육은 기간·기관·과정·경험으로 정리한다. |
| 프로젝트 목록 → 각 상세 | 프로젝트별 대표 이미지·이름·기간·서비스 요약·개인 역할·주요 기술과 상세 진입점을 둔다. |
| 상세 첫머리 → 개요 | 프로젝트명과 한 줄 설명, 대표 사진 또는 시연 캡처, 서비스 목표·대상·기능·기간·팀 구성·개인 역할·관련 자료를 담는다. |
| 기술 스택 → 주요 기능 개발 → 핵심 성과 | 사용 기술과 선택 이유, 직접 맡은 기능의 동작, 사용자가 얻은 결과나 검증된 변화를 차례로 설명한다. |
| 트러블슈팅 → 회고 → 탐색 | 사례별 질문·분석·가설·실험·전후 결과와 해당 근거 자료를 연결한다. 사례 수는 실제 경험에 맞춘다. 회고 뒤 목록 복귀와 이전·다음 프로젝트 이동을 제공한다. |

이 순서는 내용의 관계와 기본 읽기 순서를 정한다. 한 화면에 몇 항목을 묶을지, 소개를 좌우로 나눌지, 목록을 행·그리드 중 무엇으로 보일지, 상세를 어떻게 열지는 레퍼런스에 따라 정한다. 사용자가 섹션 구성이나 순서를 별도로 지정하면 그 선택을 따른다.

## 지원 대상과 첫 화면

- 지원 직무나 공고를 받았다면 직무에서 확인하려는 기술·역할·결과를 기록에서 뒷받침할 수 있는 주장과 연결한다. 방향이 미정이면 작업에 필요한 시점에 한 가지씩 묻는다. 사용자가 공통 포트폴리오를 원하면 여러 직무에서 설명할 수 있는 강점과 대표 사례를 고른다.
- 첫 화면, 짧은 자기소개, 기술 요약에서 **지원 직무, 어떤 문제를 해결하는 사람인지, 그 근거를 어디서 볼 수 있는지** 드러낸다. 표지에 해당하는 한 문장, 자기소개의 한 줄, 마무리나 연락처 앞의 메시지는 같은 강점을 전달한다.
- 자기소개는 지원 직무, 일하는 방식이나 강점, 앞으로 해결하고 싶은 문제 순서로 짧게 쓴다. 프로젝트의 세부 성과는 해당 사례에서 설명한다. 학력·교육·인턴십·활동·수상·자격증·어학 중 직무에 관련된 검증된 항목을 골라 쓴다. 사용자가 제출용 지원서나 이력서를 주면 이름, 날짜, 기관, 역할, 링크의 표기가 일치하는지 확인한다. 지원 동기·목표 달성·협업·직무 강점은 이를 보여줄 실제 사례를 고르는 근거로 활용한다.
- 첫 문장에는 직무와 실제로 해결한 문제나 만들어 낸 결과를 담는다. 읽는 사람이 프로젝트 하나를 떠올릴 수 있도록 맡은 기능, 기술적 판단, 검증할 수 있는 변화에서 단어를 고른다. 일반적인 인사말, 열정·혁신·사용자 중심 같은 근거 없는 수식어, 예시 숫자로 채운 헤드라인은 교체한다.
- 프로필 사진과 전화번호·이메일·블로그·GitHub는 공개 범위를 확인해 사용한다. 사진과 연락처의 표시 여부는 사용자와 제출 대상에 맞춘다. 프로젝트 본문은 동작과 결과가 읽히는 짧은 문장이나 항목으로 쓰고, 자기소개는 자연스러운 문장으로 쓴다.

## 기술 역량을 경험으로 증명하기

직무 관련성이 높은 기술부터 정리한다. 기술명마다 적용한 프로젝트와 구현할 수 있는 기능, 경험한 범위를 붙인다. 예를 들어 기술 이름 옆에 적용한 API, 예외 처리, 배포 단계 또는 검증에 사용한 방법을 적는다. 협업·기획·운영 직무라면 실제 사용한 업무 도구와 산출물도 포함할 수 있다.

수준 표기가 필요하면 다음 기준을 사용하고, 자기 평가를 뒷받침할 실제 경험을 옆에 쓴다.

| 수준 | 판단 기준 |
| --- | --- |
| 능숙 | 해당 기술로 기능을 독립적으로 구현한 근거가 있다. |
| 활용 | 자료를 참고해 기능을 구현했고 적용한 범위를 설명할 수 있다. |
| 학습 | 학습하거나 작은 실습에서 사용했고 경험한 한계를 설명할 수 있다. |

기술 이름과 사용 범위는 텍스트나 표로 표현한다. 숙련도는 구체적으로 할 수 있는 일과 적용 사례로 풀어 쓴다. 팀 기여는 맡은 영역·기능·코드나 문서·검증 활동으로 설명한다. 제출 대상이 수치 표기를 요구하면 산정 근거와 범위를 확인할 수 있는 수치만 적는다.

## 프로젝트 요약과 상세

지원 직무 관련성, 개인 판단을 설명할 수 있는 깊이, 검증 자료를 근거로 프로젝트 우선순위를 정한다. 대표 사례를 앞에 두고 프로젝트 카드에 **이름, 무엇을 왜 만들었는지, 기간, 팀 규모, 본인 역할, 대표 화면과 상세 링크** 중 확인된 내용을 담는다. 기술 태그는 해당 화면에서 의미 있는 기술을 중심으로 적는다. 프로젝트의 첫 실제 화면이나 별도로 고른 캡처를 카드 썸네일과 연결하고, 대표 화면에 짧은 캡션을 붙인다.

각 프로젝트 상세는 한 화면에서 읽기 쉬운 요약으로 시작한다. 목적, 기간·팀 규모·기술, 본인 역할과 직접 만든 주요 기능, 대표 문제와 확인 결과를 짧게 보여준다. 기록이 충분하면 직접 만든 핵심 기능 2~3개를 고른다. 팀 전체 기능과 본인 구현은 항목이나 역할 표시로 구분한다. 작은 프로젝트는 요약 중심으로 구성하고, 설명할 근거가 풍부한 대표 프로젝트에는 다음 내용을 더한다.

| 상세 항목 | 작성할 내용과 근거 |
| --- | --- |
| 서비스 구조와 기술 선택 | 화면·서버·데이터·외부 서비스 중 실제 요소와 데이터 흐름을 도식으로 보여주고 본인의 담당 범위를 표시한다. 어떤 제약이나 문제 때문에 기술을 골랐는지 설명한다. 검토한 대안과 선택 근거가 남아 있으면 함께 적는다. |
| 직접 만든 핵심 기능 | 기능마다 사용자 행동, 사용 기술, 본인이 구현한 방식과 오류·예외 처리 또는 테스트를 적는다. 실제 화면이나 시연을 연결하고, 코드가 필요하면 판단을 설명하는 부분만 발췌한다. 각 자료가 어떤 동작의 증거인지 캡션으로 표시한다. |
| 문제 해결 | 대표 프로젝트에서 확인 가능한 문제 하나를 골라 **현상과 발생 조건 → 원인을 좁힌 증거 → 해결 전략과 적용 방식 → 검증 결과** 순으로 쓴다. 로그·재현·측정·코드 변경이 어느 판단을 뒷받침하는지 밝힌다. |
| 성과와 회고 | 팀 성과, 기능의 변화, 개인이 확인한 결과를 구분한다. 남은 한계, 배운 점, 다음 개선을 하나의 경험에 연결한다. 협업을 다룰 때는 의견차이·역할분담·조율 중 실제 상황과 본인의 행동을 적는다. |
| AI 활용과 검증 | 실제 사용한 경우에 해당 도구와 사용 범위, 사람이 한 판단·수정, 실행·테스트·리뷰 등 검증 방법을 적는다. 효과는 근거가 있을 때만 쓴다. AI 기능 자체를 개발했다면 모델 선택 이유와 평가 방법·한계를 설명한다. |

전후 수치는 지표와 단위, 환경, 표본이나 요청 수, 비교 조건을 확인한다. 개선률은 같은 조건에서 비교할 수 있는 측정값으로 계산한다. 숫자 근거가 부족하면 실제 전후 화면, 재현 조건과 검증 결과, 관찰 가능한 정성 변화를 쓴다. 화면과 도표가 전달하는 사실은 캡션과 본문에도 표시한다.

개발 직무는 공개 허용된 GitHub 코드나 PR을 우선 연결하고, 기획·운영 직무는 실제 기획·운영 문서나 발표자료를 연결할 수 있다. 짧은 시연 영상은 확보된 경우 활용한다. 비공개 프로젝트는 공개가 승인된 설명·익명화된 증거와 접근 범위를 사용한다. 공고나 가이드에서 별도 제출 형식을 요구하면 현재 사용자 요청과 함께 확인한다.

## 편집과 검수에 넘길 내용

- 원고의 주요 주장마다 사용자 자료의 파일·절·코드나 링크를 연결해 PM과 QA가 확인할 수 있게 한다. 지원자가 면접에서 자신의 판단과 구현, 확인 결과를 설명할 수 있도록 사례의 근거와 범위를 점검한다. 수치의 조건, 팀과 개인의 구분, 확인이 필요한 내용, 링크와 미디어의 공개 가능 범위도 전달한다.
- 양식에 있던 이름·연락처·날짜·수치·기술·샘플 이미지·예시 캡션과 작성 안내는 템플릿을 읽는 데 사용한다. 실제 사이트 공개 전에는 확인된 사용자 내용, 근거 있는 캡션과 유효한 링크를 점검하고 해당 없는 선택 항목은 정리한다.
- QA는 실제 브라우저에서 첫 화면의 직무와 강점, 대표 상세로 들어가는 링크, 개인 기여와 근거, 비교 조건과 AI 검증, 캡션과 마무리 메시지, 공개 링크의 접근 범위를 확인한다. [내용과 브라우저 검수](review.md)
