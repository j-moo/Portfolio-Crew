# 형식 선택과 자료 확인

## 형식 선택과 저장소 준비

[기존 포트폴리오 여부](routing.md#최초-범위-확인)를 확인한 뒤 신규 제작이나 사용자가 요청한 사이트 이전에 아래 옵션을 사용한다. 사용자가 이미 하나를 지정했다면 그 답으로 해당 분기를 시작한다.

- **GitHub 블로그**는 GitHub 저장소에서 관리하는 GitHub Pages 포트폴리오다.
- **HTML 링크**는 GitHub 저장소 준비 없이 정적 HTML을 제작하고 브라우저에서 열리는 링크를 제공한다. 최종 링크의 접근 범위는 사용자와 정한다.

### GitHub 블로그를 선택한 경우

사용자가 이번 제작에 쓸 저장소를 이미 지정하면 소유자, 이름, 공개 범위와 현재 상태를 확인해 그곳을 사용한다. 새 저장소가 필요한 경우 아래 절차를 따른다.

1. 생성할 저장소의 소유 계정, 이름, 공개 범위를 확인한다. 계정 사이트는 `<사용자명>.github.io`, 프로젝트 사이트는 별도 저장소 이름을 사용하며 호스팅 경로가 달라진다. Pages 사용이 가능한 공개 범위를 선택할 수 있도록 계정 요금제와 조직 제한을 확인한다. 생성 전에 같은 이름의 저장소가 발견되면 주소를 보여주고 새 이름을 받는다. 사전 조회에 접근할 수 없으면 사용자에게 GitHub 생성 화면에서 이름 사용 가능 여부와 공개 범위를 확인하도록 안내한다. [GitHub Pages 사이트 만들기](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site)
2. 승인한 값으로 Chrome 플러그인이나 컴퓨터 사용 기능에서 [새 저장소 페이지](https://github.com/new)를 열어 직접 생성한다. 컴퓨터 사용 기능을 사용할 때는 해당 스킬과 도구의 확인 절차를 따른다. GitHub 플러그인이 연결되어 있으면 계정과 저장소를 확인할 때 활용한다. 연결되어 있지 않으면 연결을 안내하고, 연결 후 저장소 생성 기능이 제공되면 승인 범위에서 사용할 수 있다.
3. 로그인이나 추가 인증이 필요하면 사용자가 GitHub 화면에서 완료하도록 안내한다. 도구나 접근 권한 문제로 직접 생성을 완료할 수 없거나 사용자가 직접 만들겠다고 하면 아래 수동 절차를 제공한다. 사용자가 생성한 저장소 URL을 받는다.
4. 생성 결과 화면이나 읽기 전용 조회로 정확한 소유자, 이름, 공개 범위를 확인하고 저장소 주소를 기록한다. 직접 조회가 제한되면 합의한 소유자와 이름에 일치하는 URL 및 사용자의 생성 완료 확인을 기록하고 프로젝트 기록 단계로 진행한다. 이 경우 저장소의 조회와 게시 권한 확인은 배포 전에 완료한다. 사이트 게시와 코드 업로드는 별도의 배포 승인 단계에서 다룬다.

#### 사용자가 직접 저장소를 만드는 경우

1. GitHub에 로그인하고 [새 저장소 페이지](https://github.com/new)를 연다.
2. **Owner**에서 사용할 개인 계정 또는 조직을 선택한다.
3. **Repository name**에 앞에서 정한 이름을 입력한다. 화면에서 동일 이름이 사용 중이라고 표시되면 사용 가능한 새 이름을 고른다.
4. **Visibility**에서 앞에서 정한 공개 범위를 선택한다. 새 빈 저장소에서 시작한다면 초기 README, 라이선스, `.gitignore` 추가 여부는 사용자 선택에 따른다.
5. **Create repository**를 누르고 열린 페이지의 전체 주소를 공유해 달라고 요청한다. 주소 예시는 `https://github.com/<계정>/<저장소>`이다. 저장소를 확인한 뒤 프로젝트 기록 경로를 묻는다. [GitHub 저장소 생성 가이드](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-new-repository)

## 프로젝트 기록 확인

1. 프로젝트의 진행 기록을 어디에 모아 두었는지 묻는다. 읽을 수 있는 로컬 폴더나 저장소 경로, 또는 연결된 저장소·드라이브 폴더 링크를 받는다. 사용자가 지정한 경로에서 파일을 실제로 열어 판단한다.
2. 문서, 작업 일지, README, 변경 기록, 코드·PR 링크, 시연, 검증 자료를 살펴 프로젝트 단위로 묶는다. 각 프로젝트에서 제목, 작업 내용, 출처 예시를 확인한다. 이름만 있는 빈 폴더와 기록을 확인한 프로젝트를 구분해 발견 목록에 표시한다.
3. 경로와 함께 발견한 프로젝트 이름, 주요 근거 파일, 빠지거나 접근할 수 없는 항목을 짧게 보여준다. **“이 목록이 포트폴리오 제작에 사용할 프로젝트 기록이 맞나요?”**라고 확인한다. 승인된 프로젝트와 출처 범위를 기록한다.
4. 경로가 틀렸거나 확인할 프로젝트 기록이 없으면 확인한 상태를 알린다. 쓰기 가능한 작업 공간에 `portfolio-inputs/project-records/` 같은 폴더를 준비하고 절대 경로와 넣을 파일 예시를 안내한다. 사용자가 별도의 올바른 경로를 알려주면 그 경로를 확인한다. 프로젝트 목록이 다르다고 하면 누락되거나 잘못 분류된 항목을 확인하고, 올바른 경로나 준비한 폴더에 넣은 자료를 받는다.
5. 다시 읽어서 정정된 목록을 보여주고 승인을 요청한다. 사용자가 이번 목록을 명시적으로 승인할 때까지 1–4의 필요한 과정을 반복한다. 신규 제작은 프로젝트 목록이 확정되면 디자인 레퍼런스 경로를 요청한다. 기존 포트폴리오에 설명이나 프로젝트를 보완할 때는 바뀌는 항목의 기록만 검토하고 해당 수정 경로를 이어간다. [수정 종류에 따른 진행](routing.md#수정-종류에-따른-진행)

## 레퍼런스 목록 확인

신규 제작과 전체 디자인 방향을 바꾸는 경우 아래 목록 확인 절차를 사용한다. 일부 화면을 손볼 때는 바꿀 요소에 관한 이미지·링크·기존 스타일 기준을 먼저 요청한다. 사용자가 이미 준 레퍼런스를 열어 확인하고 해당 화면에서 어떤 특징을 가져올지 맞춘다. 일부 화면에 필요한 자료만 확인한 뒤 그 화면의 시안을 만든다. [일부 화면의 디자인 수정](design.md#일부-화면의-디자인-수정)

1. 디자인 레퍼런스 이미지가 저장된 로컬 폴더를 우선 요청한다. 첫 화면, 프로젝트 상세, 모바일 화면, 컴포넌트 등 서로 다른 화면을 비교할 수 있도록 **가능하면 10장 이상**을 권한다. 링크만 있는 경우 실제로 열어 확인할 수 있는 이미지나 화면 목록을 받는다.
2. 파일이 존재하는지와 실제 이미지로 열리는지 확인한다. 개별 레퍼런스에 고르기 쉬운 번호를 붙여 파일명 또는 링크, 열어 본 수, 열리지 않는 항목을 보여준다. 사용 가능한 수가 3~9장이면 더 추가할지 현재 목록으로 진행할지 확인한다. 세 장보다 적으면 상위 3개를 고를 수 있도록 자료를 추가해 달라고 요청한다.
3. **“이 목록이 분석할 디자인 레퍼런스가 맞나요?”**라고 묻는다. 사용 가능한 이미지가 3~9장이라면 목록을 보여주면서 이 목록 그대로 진행할지 함께 확인할 수 있다. 누락·손상·잘못된 경로가 있거나 사용자가 목록을 승인하지 않으면 쓰기 가능한 작업 공간에 `portfolio-inputs/references/` 같은 폴더를 준비하고 절대 경로를 알려준다. 사용자가 자료를 넣거나 올바른 경로를 보내면 실제로 열어 확인하고 갱신된 목록을 보여준다.
4. 실제로 열 수 있는 레퍼런스 목록을 사용자에게 승인받을 때까지 확인을 반복한다. 확인된 항목의 번호를 유지하고 [레퍼런스 분석](design.md)으로 이동한다. 최종 상위 3개를 선택할 수 있도록 목록에 열 수 있는 항목을 최소 세 개 확보한다.
