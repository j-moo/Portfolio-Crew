# 신규와 수정 경로 선택

## 최초 범위 확인

1. 새 요청에서 기존 여부가 정해지지 않았으면 **“이미 만들어 둔 포트폴리오가 있나요?”**라고만 묻고 답을 기다린다. 기존 것이 있다고 답했고 작업 유형이 아직 모호하면 다음 응답에서 **“기존 포트폴리오를 수정할까요, 새로 만들까요?”**라고 묻는다. 사용자가 이번 작업에서 알려준 답이나 같은 작업의 [진행 메모](continuity.md)에 기록된 답은 재사용한다.
2. 신규 제작이면 아직 정하지 않은 경우 GitHub 블로그와 HTML 링크 중 형식을 고르게 하고 답을 기다린다. 형식을 확인한 뒤 [형식과 자료 확인](intake.md)으로 이어간다. 사용자가 기존 사이트와 별개의 포트폴리오를 만들겠다고 하면 새 작업으로 기록한다.
3. 기존 사이트를 수정한다면 **바꿀 부분**을 먼저 묻는다. 다음 응답에서 필요할 때 사이트 주소나 로컬 소스 경로를 한 가지 요청한다. 사용자가 지정한 범위에서 편집 소스와 기준 배포본·브랜치·커밋·파일 상태를 확인한다. 재사용할 레이아웃·콘텐츠·미디어·동작과 수정할 항목, 기존 로컬 변경을 작업 메모에 적는다. [기준 버전과 검수](review.md#부분-수정의-기준-버전)
4. 주소만 있으면 현재 화면을 보고 개선안을 제시할 수 있다. 실제 수정에 필요한 저장소나 HTML 소스만 요청한다. 기존 저장소·호스팅·게시 설정을 사용하고, 이전·전면 교체가 요청되면 그 대상과 범위를 확인한다.

수정 범위를 짧게 확인하고 해당 단계에 착수한다. “프로젝트 상세에서 사용 기술 두 줄만 아래 문구로 교체”처럼 변경이 구체적이면 그 지시를 작업 범위로 사용한다. 필요한 질문을 한 번에 하나만 보내고 답을 받기 전에는 다음 확인이나 탐색을 시작하지 않는다.

## 수정 종류에 따른 진행

구체적인 부분 편집은 [반복 편집 지침](iterative-editing.md)에 따라 메인 에이전트가 직접 수행한다. 아래 표의 역할 분담과 중간 승인은 원고·디자인 선택이 열려 있거나 여러 작업의 인계가 필요한 개편에 사용한다.

| 사용자가 바꾸려는 부분 | 시작 단계와 진행 방식 | 주로 협업할 역할 |
| --- | --- | --- |
| **내용** | 현재 문구와 수정 범위를 확인한다. 사용자가 준 문구를 적용하거나, 프로젝트 경험·수치·이미지를 추가할 때는 해당 항목의 근거와 [작성 기준](portfolio-writing.md)을 확인한다. 지원 직무가 바뀌면 새 직무에 영향을 받는 첫 화면·기술 요약·대표 사례만 다시 검토한다. 보완 원고가 필요하면 전후 문구와 근거를 보여주고 확인받는다. | **PM과 콘텐츠 에디터**가 원고를 주고받는다. 화면에 반영할 때는 프런트엔드 개발자에게 편집 위치와 승인 문구를 넘긴다. |
| **디자인** | 많은 원본은 [HTML 토너먼트](design.md#레퍼런스-선택)로 추리고, 후보를 자기 콘텐츠로 보고 싶다는 요청은 [후보별 시안 비교](design.md#후보별-포트폴리오-시안-비교)로 진행한다. 부분 수정은 승인된 기준이나 기존 스타일을 사용한다. 해당 변경의 [아트 디렉션](design.md#아트-디렉션과-승인)을 승인받고 토큰·컴포넌트·에셋을 준비한 뒤 영향받는 화면만 구현하고 비교한다. | **PM과 UI 디자이너**가 원본 기준과 시안을 넘긴다. 프런트엔드 개발자가 컴포넌트와 섹션을 구현하고 QA/배포가 시각 검수 라운드를 실행한다. |
| **탐색 구조·프로젝트 추가** | 바뀔 진입점과 상세 페이지를 확인하고 필요한 부분의 사이트맵과 콘텐츠를 검토한다. 새 프로젝트는 그 프로젝트의 기록과 공개 미디어를 확인한다. 새로 바뀌는 링크와 기존 복귀 동선을 검수한다. | **PM·웹 기획자·콘텐츠 에디터**가 구조와 원고를 맞춘 뒤 UI 또는 프런트엔드에 필요한 작업을 넘긴다. |
| **모션·기능** | 기존 동작, 재현 조건, 기대 동작을 확인한다. 새 모션이라면 실행 예제와 축소 모션 동작을 보여주고 효과를 확인받는다. 기존 기능 복구는 기준 버전과 비교해 검수한다. 모션과 함께 디자인 방향이 바뀌면 해당 화면의 레퍼런스도 확인한다. | **PM·프런트엔드 개발자·QA/배포**가 재현과 수정본을 확인한다. 시각 효과가 달라지는 경우 UI 디자이너와 모션 명세를 맞춘다. |
| **게시·링크** | 수정한 버전, 사이트 주소, 저장소·브랜치 또는 호스팅 경로를 확인한다. 요청으로 대상과 공개 범위가 정해지면 게시하고 실제 링크를 검수한다. 대상이 모호하면 필요한 결정만 확인한다. | **PM과 QA/배포**가 대상과 승인 증거를 확인한다. |

하나의 요청에 여러 수정 종류가 있으면 공통 범위와 영향받는 화면을 한 번 정한다. 작업을 의존 순서대로 연결하고 겹치는 시안·원고·검수는 함께 보여준다. 예를 들어 소개 문장과 첫 화면 디자인을 함께 바꿀 때는 콘텐츠 에디터가 원고를 확정하고, 디자이너가 그 원고를 시안에 넣어 사용자에게 보여준다. [팀 제작과 인계](production.md)

내용만 바꾼 경우 해당 상세의 기존 레이아웃과 연결된 갤러리·영상·기록·복귀 동선을 기준본과 비교한다. 디자인이나 모션을 바꾼 경우 해당 화면의 콘텐츠와 기존 동선을 함께 비교한다. 같은 파일 안에 여러 기능이 있으면 파일 변경과 실제 브라우저 동작을 각각 확인한다. [브라우저 검수](review.md)

## 제작 중 경로 조정

1. 신규 제작과 기존 수정 중 모두, 피드백을 받으면 PM이 **달라지는 요구, 현재 단계, 승인한 결과물, 의존하는 작업**을 대조한다. 기존 작업의 진행 메모에서 계속 기록한다.
2. 영향이 시작되는 단계에서 필요한 작업을 한다. 원고만 달라지면 PM과 에디터가 검토하고, 레이아웃에 영향이 있으면 해당 시안도 확인한다. 승인한 디자인 방향 안의 색·간격 조정은 현재 아트 디렉션과 시안을 사용한다. 방향이나 기준 레퍼런스가 달라지면 아트 디렉션에서 바뀐 부분을 다시 승인받은 뒤 해당 구현에 착수한다. 효과만 달라지면 모션 명세와 미리보기를 갱신한다.
3. 이미 승인한 산출물 가운데 영향이 없는 것과 기존 협업 담당자를 재사용한다. 단계 순서를 조정할 때는 필요한 자료, 다음 담당자, 사용자에게 다시 보여줄 산출물을 PM이 정리한다. 검수 범위는 변경 항목과 영향을 받을 수 있는 연결 동선으로 잡는다.
4. 바뀐 결과와 다음 행동을 사용자에게 보여주고 해당 결정의 승인을 받는다. 변경된 범위, 유효한 승인, 현재 단계와 대기 중인 요청을 [진행 메모](continuity.md)에 기록한다.

사용자가 결과가 레퍼런스와 어긋난다고 알려주면 확정한 원본과 시안이나 구현을 다시 비교한다. 기준을 새로 고르는 요청에는 확인된 목록으로 토너먼트 HTML을 준비한다. 사용자 프로젝트와 원고는 기존 승인을 이어 쓴다.
